Two ways to connect

So far the agent has only used your machine

  • Everything this week stayed in one place: your files, your code, and public web pages.
  • Most of what a real project needs lives elsewhere: the Census, your Zotero library, a journal database, a government portal.
  • Those are other websites and apps, and the agent cannot use them until you give it a way in.
  • Today's question: how does the agent work with a website or an app that is not on your machine?

Two ways the agent works with other websites and apps

  • Every outside website or app poses the same problem: the agent needs a way to talk to it.
  • There are two answers:
    • the site has an API: it accepts requests from programs, and the agent writes the request
    • you connect the app once through MCP, and from then on the agent uses it directly
  • The morning is about APIs. MCP comes after the break.

APIs · try it on the right

An API accepts requests from programs

  • Many data sites offer an API: an address where a program, rather than a person, asks for data.
  • Each site defines its own. The Census has one, arXiv has one, and they all differ.
  • Using an API means writing code to send the request, and writing that code is exactly what the agent does well.

Constructing an API call: endpoint and parameters

  • Our teaching example is arXiv, the open paper archive. Its API needs no account.
  • Paste this into a browser:
http://export.arxiv.org/api/query?search_query=all:electron&start=0&max_results=5
  • The endpoint is the part before the question mark: where you are calling.
  • The parameters are the part after it: what you are asking for. Here: search for "electron", return the first 5 records.
  • What comes back is not a webpage. It is structured text, one record per paper, with title, authors, and date as named fields.

The agent writes the API code for you

  • In a programming course you would now read the API documentation and write the request loop yourself.
  • Here you say: "Get the 100 most recent arXiv papers mentioning 'election', with title, authors, and date, as a CSV." The agent reads the documentation and writes the loop.
  • Your job moves up one level: check the CSV against the site, and make sure the agent respects the site's rate limits.

Collecting data: APIs that return data · do it on the right

Where research data comes from

  • The arXiv pull you just saw is data collection: an API that returns records, and a loop that turns them into a table.
  • The same pattern covers most sources: the Census, a city open-data portal, a journal database.
  • Two fallbacks when there is no API:
    • a web page with a table on it: the agent reads the page itself and extracts the table
    • a file to download and unpack, for example a CSV inside a ZIP
  • You still choose the source, choose the variables, and decide the amount.

Verify your collection

  • These agents are weakest at gathering data.
  • On a social-science replication benchmark, agents scored about 96 at running an analysis and about 31 at finding the data it needed.
  • Scrapes will break and fields will be wrong, so check every pull against the source.

Nguyen et al., "ReplicatorBench" (2026), arXiv:2602.11354.

Some APIs need a key

  • Open APIs like arXiv answer anyone. Most others hand out a key: a password for programs, usually free to request.
  • The site uses the key to know who is asking, to limit how fast you pull, and sometimes to bill.
  • You paste your key in once, and the agent uses it from then on. The key lives in a file, never inside the code you share.

No API: the agent reads the page itself

  • Point it at the page: "Get the monthly unemployment table from this URL and put it in a CSV."
  • The agent reads the page, finds the table, and saves it.
  • Watch for the problems it should flag: a table split across pages, footnotes mixed into cells, and a site that asks you not to scrape.
  • If a site's terms forbid scraping, stop and find another source.

Track raw pull sources

  • Save the raw result once, before any cleaning, and never overwrite that copy.
  • Have the agent write the source, the date, and the exact query next to the file.
  • Months later, you use that note to answer "where did this number come from."

Check your results

  • Open the raw file and read the first few rows yourself.
  • Manually compare some values against the source page or the API.
  • Move the data into your analysis only after it matches.

Turn a repeated pull into a Skill

  • A pull you will run again, such as grabbing this month's new records, is worth packaging.
  • Turn the steps into a Skill, the same way you did on Wednesday, so next time is one command.
  • You can share the Skill, and a labmate can then run the same pull using their own key.

Scaling a pull: script or subagents?

  • One question matters: are the steps the same for every piece?
  • If the steps are the same — 50 calls to one API, each with a different state code — that is a loop in a script, and no agent is needed.
  • If every piece is different — 10 state websites, each with its own layout — that is subagent work, and each copy figures out its own page.

Coding data at scale: an API that returns judgments · try it on the right

The API you have been using all week

  • The model itself is a website with an API: you send it text and instructions, and it sends back an answer.
  • The chat window and Claude Code are wrappers around that API. Every message this week went through it.
  • arXiv's API returns data. The model's API returns a judgment. Both are the same mechanism: a request goes out, a structured answer comes back.

Coding data through the model's API

  • On Monday you coded twenty cases by pasting them into the chat. That works for twenty, not for twenty thousand.
  • At scale, the same task becomes a script: for each case, the script sends the codebook and one text to the model's API, and stores the label that comes back.
  • Coding data this way is now a standard workflow in social science, with a growing methods literature on when to trust it.

What the script sends, one case at a time

  • Each request contains your codebook and one text case.
  • Sent: "Codebook: 1 = mentions cost, 0 = does not. Text: 'The premiums went up again this year.' Answer with the code only."
  • Returned: "1".
  • The loop repeats this once per case and writes each answer next to its case in a CSV.

Many model APIs, one request format

  • Every major lab sells its model the same way, and the request format is nearly identical across OpenAI, Anthropic, and Google.
  • OpenRouter puts the whole market behind one address: one account, one key, four hundred models. You pick the model by its name inside the request.
  • That makes a robustness check cheap: rerun the same coding with a second model, and report the agreement, the same way you would for two human coders.
  • When the text cannot leave your machine at all, such as interviews under an IRB protocol, the same request shape also works against a model running on your own laptop.
  • OpenRouter can even pick the model for you (model = openrouter/auto), routed by what other users run for similar tasks. Fun to try, but for coded data you pin one model and report it. The model is part of your method.

The same case, three models

  • One request, one codebook, one text case. The only thing that changes is the model's name.
  • Send it to a strong model, a mid one, and a cheap one, and read the three codes side by side.
  • In our test run, a small model miscoded this case while larger models coded it correctly.
  • The model is a choice you report, like a coder, not a fixed part of the machine.
  • The check does not change: hand-code a sample, compare, and report the agreement before you run the rest.

MCP

What MCP is: a pre-packaged API

  • Gmail has an API. So do Google Calendar, Slack, and Zotero. So why a second way in?
  • MCP is not another source. It is an API packaged for agents: someone wraps a site's API into ready-made tools and handles the login, and you connect it once with a click.
  • After that the agent uses the app directly — "what is on my calendar Thursday?" — with no code written and no key pasted.

Why MCP exists

  • The AI most people use — the chat app on their phone or desktop — cannot run code at all. Someone must hand it tools, and MCP is the standard way to hand them.
  • It also carries the login: for a Gmail or Google Drive connector you sign in once in the browser. You could not get that access by writing code without a developer account.
  • One standard works across AI apps: Claude and ChatGPT both speak it, and the same connector serves both.

API or MCP: when to use which

  • In Claude Code, which writes code fluently, the API route often does the same job with less overhead. Our Zotero setup runs on its API, no MCP involved.
  • In the chat apps — claude.ai, Claude Desktop, your phone — MCP is the only way in, and it is how you connect Gmail, Drive, Slack, or Notion there.

Finding literature

Literature is where fabrication hurts most

  • Ask a bare chatbot for ten citations, and some will be invented. A text predictor produces references that only sound real.
  • This cannot be fixed from inside the model: it has no way to check its own memory, and "please double-check" just makes it predict again.
  • Verification needs an outside authority — a source of record the reference can be checked against.
  • That is what the morning's APIs are for: every reference must arrive through an API, with its real metadata, from a source of record.

My own workflow: four steps

  • You are writing, and a claim needs a citation. The citation must be real.
  • Zotero is where your references live: it holds your library and builds your bibliography.
  • This is how I solve it myself, in four steps:
    • 1. search my Zotero library — is the paper already there?
    • 2. if not, search OpenAlex — find it, with its real metadata
    • 3. add it to Zotero — write it into my library
    • 4. one written rule for the agent: only works that are in my Zotero can be cited
  • Steps 1 to 3 are API calls like the morning's. Step 4 makes the agent follow them. The next cards take them one at a time.

Step 1: is it already in my library?

  • Every citation starts with this question, before any search of the web.
  • The agent asks it through the Zotero API: search your library by title words, by author, or by DOI.
  • A miss is not proof of absence. The paper may be filed under different words, so search a second way before concluding it is not there.

Step 2: find it in OpenAlex

  • OpenAlex is a free, open index of more than 250 million scholarly works, all fields. The same kind of API as arXiv's, plus citation links between papers.
  • Search by topic or by title. Follow the citations of what you find to the papers nearby.
  • What comes back is a database record: title, authors, year, venue, DOI.
  • That record, not the model's memory, is what goes into your draft.

Why step 2 is slow

  • Every database limits how fast a program can ask. They protect their servers, and they do not want their whole collection copied.
  • arXiv asks for one request every three seconds. Semantic Scholar often refuses without a key. OpenAlex is generous if you send your email along.
  • Hit the limit and the site answers "too many requests". The right response is to slow down, wait, and retry.
  • In practice this, not the code, is what makes the search step slow. Plan for minutes, not seconds.

Step 3: write it into Zotero

  • Adding the paper to your library is a write request to the Zotero API, with your key. The same mechanics as every API call this morning.
  • The record lands with its metadata attached, exactly as OpenAlex returned it.
  • Your bibliography is then generated from the library, so no line in it was ever typed from memory.

Step 4: one rule the agent cannot skip

  • Steps 1 to 3 only work if the agent never goes around them.
  • So the rule goes into the agent's instruction file, in writing: "Only cite works that are in my Zotero library. If a work is not there, stop and tell me."
  • With that line, a citation cannot enter a draft from the model's memory. The only way in is the three steps above.

Checking a finished draft works the same way

  • The three steps keep fake references out. The same idea also checks references that are already on the page:
    • citation check: look up every reference in the draft against Crossref or OpenAlex. The DOI, title, authors, and venue must match.
    • retraction check: run the references against the Retraction Watch database, now part of Crossref.
    • reading your own library: the agent answers from the PDFs in your Zotero, not from its memory of the literature.
  • The rule under all three: where a database of record exists, check against it. Never trust the model's memory.

Subagents speed up steps 1 and 2

  • Tuesday's subagents come back here, because the steps repeat.
  • Step 1 can run in parallel: a draft cites thirty works, and one subagent per work checks the library at the same time.
  • Step 2 can run in parallel too: several searches run at once, with different keywords or different databases.
  • Step 3 stays sequential: one writer adds the keepers to the library, so nothing is added twice.

What this section showed

  • Monday's WVS demo was one chart from one dataset. This workflow is much more complex: four steps, three APIs, and one written rule.
  • The shape is the standard one for a complex task:
    • plan first: plan mode turns the vague goal into concrete steps
    • run the steps separately, and check each one
    • inside a step, run the independent pieces in parallel with subagents
  • It solves a real failure: fabricated citations.
  • My own version is not finished; I am still fixing parts of it. It is a working example. Take the design and build your own.
