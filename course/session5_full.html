Takeaways

Turn your analysis into a website · do it on the right

Definition of building

  • You can run an analysis and nobody else can use it.
  • Today, building means one specific thing: turning your analysis into a webpage that other people can open and read.
  • The page shows your question, one figure or table from output/, and one sentence saying what you found.
  • The division of labor is the same as Monday. You specify and verify, and the agent writes the code.

How a web page works

  • Every webpage, from a personal site to a results page, has three layers:
    • what the reader sees, which is the structure, the style, and the behavior
    • What changes on the page and which are the inputs and filters?
    • The numbers come from your analysis output.
  • You will let the agent write all of these layers.
  • Learn the layers, which lets you check the agent's work. Open the page, click through it, and verify the numbers against your output.

Keeping private data on your own machine · do it on the right

When your data cannot leave your computer

  • Some data cannot go to a company's servers. This includes human subjects, restricted records, and anything under an IRB or a data agreement.
  • Default tools send your files to Anthropic or OpenAI, and you cannot use those tools for that data.
  • Run the tool on an open-source model on your own machine, which is the fix and nothing leaves the machine.

How to keep it local

  • Ollama is a free program and runs open-source models like Llama or Qwen. You can run them on your laptop.
  • You can run Codex against a local model with codex --oss and also point Claude Code at the local server and use two settings and a model name for this. Ollera is the local model server and speaks both tools’ protocols.
  • Claude Code supports this route through Ollama, but it does not support it through Anthropic. For Codex, the --oss flag is official.
  • Set the sandbox to your project folder and turn the network off.
  • Local models are slower and weaker than Claude or GPT, and you use them only when the data requires it.

What makes a local model fail

  • Silent truncation. The agent sends about 23,000 tokens per request, which are its own instructions and tool definitions. A local server has a smaller context window, so it cuts the tokens off. There is no error message, and the model loses its instructions and returns nothing. To fix this, start the server with a 32k context: OLLAMA_CONTEXT_LENGTH=32768 ollama serve.
  • Memory goes to the context window. The same 2.5 GB model uses 4.8 GB of memory at 16k context, 7.8 GB at 32k, and 42 GB at Ollama’s default, and on a 16 GB laptop, the default context causes the machine to swap or the model to fail.
  • Model size. A 3B model answers questions but cannot follow the agent’s tool instructions at all. A 4B model barely completes a one-file task in minutes, and a serious setup starts around 20B and needs 16 GB of memory or more.

Use local tools for daily private work

  • Claude Code’s instructions are made for a frontier cloud model, and a local model performs below its own level inside them.
  • Local model tools use smaller instructions and work better with the same model. Aider (aider --model ollama/qwen3-coder, saves every change as a commit) and OpenCode are the two established choices.
  • Claude Code on Ollama shows the tool and the model are separate, so use one of these local-first tools on the same Ollama for the sensitive project.

Other models in this agent · do it on the right

A cheaper model for the same agent

  • Many companies sell frontier open-weight models and use interfaces that speak Anthropic’s protocol. DeepSeek, Kimi (Moonshot), and GLM (Z.ai) all publish an address, and Claude Code can talk to these addresses directly.
  • To switch, you need one environment variable and an API key from that company, and it costs much less than Anthropic’s price, and some companies sell monthly coding plans for this exact use.
  • This lowers your price. It does not protect your privacy. Your data still leaves your machine. It goes to a different company’s servers now. This route is no better than the default for data under an IRB or a data agreement. The server location can make compliance harder.
  • The model company supports this route and Anthropic tolerates it, but if it breaks, no support team will help you. Quality changes by provider and month, and the best open models test close to the closed frontier.
  • This route does not reach GPT, and OpenAI does not publish an Anthropic-compatible address. You need a fragile translation proxy in the middle to reach GPT, so use Codex for GPT.

A second opinion from another model family

  • The agent can run any command-line program, and another agent’s CLI is a command-line program. One saved command sends a question to Codex, which returns the answer for comparison.
  • Models in one family use the same training data and make the same mistakes, so their errors are correlated, and when Claude checks Claude, it is like reading the same answer twice, but a reviewer from a different family is more like an independent draw.
  • Confidence rises when both families agree, but check the parts where they disagree yourself.
  • The second model does not know about your conversation, and everything it needs must be in the question you send.
  • Read the second opinion and decide for yourself, and if the agent applies it without reading, no answer is checked.
  • The same command goes to Gemini (gemini -p) or a local model (ollama run). The local model gives a second opinion and is free and fully offline.

What the full course includes

  • Build and deploy real tools using your research.

Before you build bigger: four questions

  • Can you check every result yourself, and if so, you do not need to build anything.
  • Is checking a result cheaper than making it? If so, you are the quality control and the general agent is enough.
  • Do the steps stay the same every time? If they are the same, it is a script, and if they change for every input, it is a real agent loop.
  • Can you build a gold standard to test it, and if you cannot, do not produce any data with it.
  • This full course answers these questions, and people often make a mistake and skip ahead and say, "I do this 300 times, so I need an agent," but a script or nothing was the correct answer.

Who splits the work?

  • Today's capstone fits in one conversation, but Your next real project will not.
  • The next design question is decomposition: if a task is too large for one session, who splits it up, you or the agent?
  • Both agents cover the full range:
    • You decompose fully. A shell loop calls claude -p (Codex: codex exec) once per item on a list you wrote, when you already know every piece.
    • You plan, the agent executes. Use Plan mode when you know the goal but need to think about the steps, and it shows you a plan for approval before it changes any files.
    • You frame, the agent splits. Do A, B, and C at the same time using different subagents. This works if the parts are independent and if summaries are enough, and Thursday's parallel paper reading showed this.
    • The agent decomposes fully. A workflow has the agent write an orchestration script. This script runs dozens of subagents and can do a repository-wide audit or a hundred-item migration.

Before you parallelize

  • Four rules of thumb from Anthropic's own multi-agent engineering:
    • Independence. Only subtasks that do not depend on each other's output can run in parallel. A chain of dependent steps gains nothing.
    • Cost. A multi-agent run uses about 15 times more tokens than a single chat, so the task must be worth it.
    • Focus. Three agents have sharp and separate briefs, and they beat five agents who have scattered briefs.
    • Independent review. An author's context learns to overlook things, but a reviewer agent has a clean context and catches those errors, and journals use outside referees for this same reason.

After five days

  • Use one repository for each project and let it grow like this one did.
  • Use your instruction files and Skills on the next project starting from day one.
  • Subagents and workflows are useful when a task is too big for one session.

Local and open models: how good are they?

  • Small local models in the 7B class lose 15 to 40 points on agentic benchmarks and hallucinate tool calls. Frontier open-weights models like Kimi K2.6 and Qwen 3.6 are close to the closed frontier and within a few points.
  • You used this earlier today in the second-opinion command.

Continued practice

  • Continue using the repository, and use the agent for one task per week. The instructions file grows as the project grows.
  • Free self-paced material if you want more:
    • Anthropic Academy: short courses on Claude Code, from beginner up.
    • DeepLearning.AI: "Claude Code: An agent-like coding assistant."
  • The habit that is more important than any tool: an unverified result is not a result.

Hands-on

Step 1

Build a results page

Everyone builds the same thing: one HTML page in your own repository that presents this week's analysis. You have 100 minutes.

  • The page states your question in one sentence.
  • The page shows one figure or one table from output/.
  • The page ends with one sentence saying what you found.
Step 2

Rules of the build

  • Everything goes into your own repository.
  • Follow the Tuesday rule. The agent suggests a plan, and you review the plan. Then the agent builds.
  • Check everything first, then polish, and check every number on the page against the files in output/.
  • Commit at every stage of your work, so this lets you step back at any time.
Step 3

If you finish early

  • Add one control: a country selector or a year slider that filters the chart.
  • Then add a second page for a second result, with a link between the two pages.
  • Do not start an app and do not touch your instructions file. Today is about the page.

A starting prompt:

Build a webpage that shows the chart in output/. Add one control, a country selector, that filters the chart. Show me a plan first, then build it. Do not change my analysis code.copy
Commit before each big change, so you can step back to a working stage if something breaks.
Step 1

Install a local model

Install Ollama, pick a model from your memory, and start the server with a 32k context.

curl -fsSL https://ollama.com/install.sh | shcopy

16 GB laptop: ollama pull qwen3:4b and 32 GB or more: ollama pull qwen3-coder:30b.

OLLAMA_CONTEXT_LENGTH=32768 ollama servecopy
Step 2

Point your agent at it

Set these variables for Claude Code, which makes it talk to your local server instead of the company's servers, and name a model you have downloaded.

export ANTHROPIC_AUTH_TOKEN=ollama export ANTHROPIC_API_KEY="" export ANTHROPIC_BASE_URL=http://localhost:11434 claude --model qwen3.5copy
  • For Codex: codex --oss starts it against the local model instead.
  • Use /model and the model's name to switch models in the session. The variable chooses the server, and the name chooses the model.
  • Turn off the network and set the sandbox to your project folder.
Step 3

Check that nothing leaves

  • Use ordinary data first, turn the network off, and ask the local agent a question.
  • Turn off your wifi and give it a task. If it still works, nothing was going out.
  • You can show this proof to an IRB, and the data stayed on the machine.
  • Watch it work: ollama ps shows the model loaded and answering in a second terminal.
Step 4

For the real project, switch to a local-first tool

python -m pip install aider-install && aider-install aider --model ollama/qwen3-coder:30bcopy

This runs the same local model in a specific tool and it saves every change as a commit.

Step 1

Point the agent at a cheaper hosted model

Get an API key from the provider, point the same agent to its address, and use DeepSeek as the example:

export ANTHROPIC_BASE_URL=https://api.deepseek.com/anthropic export ANTHROPIC_AUTH_TOKEN=YOUR_DEEPSEEK_KEY export ANTHROPIC_MODEL=deepseek-reasoner claudecopy
  • Kimi: https://api.moonshot.ai/anthropic and GLM: https://api.z.ai/api/anthropic. Each provider has documentation which lists the current model names.
  • Open a fresh terminal to go back to Claude and the variables live only in the shell that set them.
Step 2

Save a second-opinion command

Make .claude/commands/consult-codex.md in your project:

--- description: Second opinion from Codex allowed-tools: Bash(codex exec:*), Read --- Ask Codex for an independent opinion on: $ARGUMENTS If a file is referenced, Read it and inline the relevant part. Run exactly: codex exec --skip-git-repo-check --sandbox read-only "<question + context>" < /dev/null Report Codex's answer as Codex's, then say where you agree and disagree. Never edit files from this command.copy
  • The < /dev/null is important, and without it, Codex waits for input forever.
  • Costs charge your ChatGPT account but do not charge your Claude plan.
Step 3

Use it on a real question

/consult-codex is mean imputation biasing my variance estimates downward?copy
  • Read both answers. If they agree, your confidence goes up, and if they disagree, check them by hand.
  • Do not ask it to apply the advice; that decision stays with you.
