Breaking work into clear steps · do it on the right

Five stages of any analysis

  • Every empirical project moves through the same five stages:
    • Data preparation. Where does the data come from, and is it clean?
    • Exploratory analysis. What patterns are there?
    • Statistical modeling. Does the hypothesis hold?
    • Output and reporting. How do you present it?
    • Reproducible publication. Can someone else replicate it?
  • Today you work through stages 1 through 4 on your own data. Stage 5 is a build option on Friday.

What the agent contributes at each stage

StageWhat you delegateWhat you keep
Preparerecoding, merging, type fixeswhat counts as missing
Exploresummaries, distributions, diagnosticswhich patterns matter
Modelwriting and running the estimationthe specification
Reportformatting tables and figureswhat the result means
  • The agent does the typing, and you make the choices.

The choices you did not state

  • Any real task has choices you did not state: which variable, how to treat missing codes, whether to weight, which sample.
  • Where you leave a gap, the agent fills it with the average analyst’s defaults, and the average analyst is not you.
  • Each of those choices is defensible, and none of them was yours. That is why you write the plan first.

Who writes the plan

  • Three ways, all legitimate:
    • You plan. You break the work into stages yourself and hand the agent one stage at a time.
    • The agent plans. In plan mode it reads your project, proposes a plan, and runs nothing until you approve.
    • You draft, the agent refines. You write the plan, hand it over, and the agent tells you what is missing, what order is wrong, and what it would cut.
  • Today’s exercise uses the third way, on your own project.
  • Both tools enter plan mode with Shift+Tab. Claude Code cycles plan mode, ask-first, and auto-accept; Codex cycles Plan, Pair, and Execute, and /plan jumps straight there.
  • Whoever drafts it, the plan is yours after you edit it. Do not approve a step you cannot explain.

Verifying your results · do it on the right

Why you always check

  • The agent is fluent, and fluent output can still be wrong.
  • It will not tell you when it guessed; a wrong number looks exactly like a right one.
  • Nothing counts as a result until you have checked it yourself.

Ways to check a result

  • Recompute one number a second way, in software you already trust, and see if it matches.
  • Compare it against something you already know: a published figure, a total that must add up, or a number you expected.
  • Read the code and the choices it made: which cases it dropped, how it treated missing values, whether it weighted.
  • Look at the plain features of the data: the row count, the missing counts, the smallest and largest values.
  • Change one input, and check the output moves the way it should.
  • Have a fresh session or a second agent redo the step, and compare the two.

Worked example: Monday's chart

  • Monday's WVS chart looked convincing. It was probably wrong in at least one place:
    • Right variable? WVS has several politics items: interest, importance, action. Check the codebook.
    • Missing values? WVS codes "don't know / refused" as -1 to -5; averaging those in corrupts every country mean.
    • Weights? WVS has survey weights; unweighted means can mislead.
    • Scale direction? 1 = very important, 4 = not at all; the chart may run in the opposite direction from what you expect.
  • Every one of these is invisible in the picture and visible in the code.

Several agents at once: for speed, and for checking · do it on the right

You can run more than one agent

  • Open several agents at once, give each one a separate job, and they work at the same time.
  • On the same cleaned dataset: one writes the descriptive table, one draws the chart, one drafts the README.
  • The jobs have to be independent, so none of them waits on another. Cleaning and charting are not independent: the chart needs the cleaned data.
Live demo

Three agents at once

  • I open three agents and give each an independent task on the same cleaned dataset.
  • All three run at the same time and finish sooner than one agent doing them one after another.

Subagents: one agent runs the others

  • Instead of opening the agents yourself, you can tell one agent to do it: "write the table, the chart, and the README from the cleaned data, using a separate helper for each."
  • These helpers are called subagents. Each gets its own context, does one assigned task, and returns a short report to the main agent.
  • The main conversation receives only the reports, so it does not fill up with the helpers’ working text.
  • You ask for them in plain language: "in parallel, using separate subagents" is enough. There is nothing to configure.

Which arrangement for which job

  • The difference between the two is who coordinates the work, you or the main agent.
  • Open several sessions yourself when the tasks are independent and you want to watch and steer each one.
  • Use subagents when the results must be combined afterward. The main agent receives every report, so it can require one format for all of them.
  • When the combining step needs judgment, do it yourself: run separate sessions and merge the results.
  • On Thursday you use subagents on a real case: five papers read in parallel, then one synthesis.

Sessions can message each other

  • In both tools, one open session can send a message to another.
  • Claude Code: /msg list shows your reachable sessions, and /msg sends to one. This works without any setup, including to sessions on other machines.
  • Codex: a session can queue a message to another local or remote session.
  • Use it to coordinate your open sessions: the session that finishes cleaning tells the modeling session that the data is ready.
  • Shared files and git are the slower way to pass work between sessions. They also leave a record a collaborator can read later.

Two reasons to run more than one

  • One reason is speed: split a task into five independent pieces, run five agents, and a five-minute wait becomes about one minute.
  • If one piece needs another’s output, it waits, and the speedup is gone.
  • The other reason is checking: two subagents doing the same job cannot see each other, so comparing their results tells you something one run cannot.
  • Research already works this way: two coders code the same sample, and a replication is run by someone else.

Plan on the advanced model, execute on the cheap one

  • The advanced model plans better and costs more. The cheap model is fast and costs almost nothing.
  • Planning needs the better model. Execution is mechanical. Spend the expensive tokens on planning.
  • One prompt does it:
Make the plan and review the results yourself. Run the pieces with subagents on a cheaper model.
  • You set your own session’s model with /model in both tools.
  • Tomorrow you write this down once, in a file the agent reads every time.

What running them costs

  • The tool charges by usage, measured in units called tokens, and each plan has a limit.
  • Several agents at once, or one agent working for a long time, spend that usage faster.
  • Check your usage now and then.
Exercise

The same model in R and in Python

  • One instruction: "Implement my model spec twice, one subagent in R and one in Python, working independently. Then put the two coefficient tables side by side and report every difference."
  • If the tables match, the result does not depend on the software.
  • If they differ, a default differed: how one language handles missing values, standard errors, or factor levels. Which one you meant is your call.
  • No third agent is needed: the main agent compares the two tables, and judging a difference is yours.

Turning text into variables

  • A lot of social-science data starts as text: open-ended answers, interview transcripts, documents, news.
  • The agent can read each case and assign a code, the way a research assistant would.
  • That turns text into a variable you can count and model.
  • What you build in this unit is the codebook: the coding rules you give the agent. You sharpen it by having two coders work independently and reading where they disagree.
  • Coding thousands of cases is a script's job, and it gets one card at the end.
Exercise

A worked example: consumer complaints

  • The running example: the CFPB Consumer Complaint Database — 3.8 million free-text complaints about banks and lenders, public and downloadable without registration (consumerfinance.gov). The question: what kind of wrong does the writer say was done to them?
  • The codebook is categories, each with a rule and a real example:
    • Unauthorized — money moved or an account opened without consent. "My credit score is fine and for some reason the rate they charged me is 22%" is not this; "an account was opened in my name when I was too young to have one" is.
    • Inaccurate record — the company reports something wrong, and the remedy asked for is correction, not money. "The debt was already removed, and they keep adding it back to my credit report."
    • Unfair charge — the account is mine, but the fee, rate, or terms are disputed. "I was approved, and the interest rate they charged me is 22%."
    • Service failure — the company would not act or could not be reached. "The website has been down for months and no email is ever answered."
  • These categories cut across the database’s own labels, so the official labels can serve as a third coder to compare against.
  • Give the agent the codebook and twenty cases, and read what it returns. Where it codes differently than you would, the rule was unclear; fix the rule, not the answer.

The pilot: two coders, one codebook

  • This is the main exercise of the unit.
  • Two subagents each code the same ten cases with your codebook, independently.
  • Where they disagree, the codebook was unclear. Discuss the disagreements, fix the rules, run again, and watch agreement rise.
  • What you keep at the end is the revised codebook.
  • One caution: the two subagents run on the same model, so their agreement is like one coder coding twice. Your own hand codes remain the reference.

Check the agent's codes against your own

  • Hand-code a random sample yourself, then compare the agent's codes to yours.
  • Report the agreement, the same way you would for two human coders.
  • Low agreement means the codebook is vague or the task is too hard; fix that before you trust the rest.

Coding at scale

  • For dozens of cases, the agent codes them in the conversation. That is where you develop the codebook, and that is the work of today.
  • For thousands, do not code in the agent at all. Reading thousands of cases in a conversation uses up money and context, drifts as the session fills, and cannot be rerun.
  • Instead, the agent writes a script: each case goes to a model API with the frozen codebook as the prompt, on a cheap model, and the labels are saved to a CSV. The script can be rerun, resumed, and it costs only cents.
  • The frozen prompt in that script is your measurement instrument.

Why long sessions drift

  • As a session grows, the text the agent is holding fills up with files, outputs, and errors.
  • Your instructions from the first hour get crowded out, and the agent slowly reverts to its own defaults.
  • Tomorrow morning it remembers nothing at all.
  • Tomorrow's session builds the fix: instructions that persist outside the conversation.

Hands-on

Step 1

Say your problem in one sentence

Start from the sentence you wrote last night. Write it at the top of a new file, in plain words a colleague outside your field would understand.

Step 2

Write your own plan

Under the sentence, break the work into steps, as concretely as you can. Use the stages as a guide: prepare, explore, model, report.

  • Name the actual variables, the actual files, the actual model.
  • Where you are unsure, write the question instead of skipping it.
Step 3

Have the agent refine it

Enter plan mode (Shift+Tab in both tools; /plan in Codex), then:

This is my problem and this is my plan. Refine it: what is missing, what order is wrong, what would you cut, and which of my choices would another analyst make differently?copy
Step 4

Judge the refined plan

  • Go through its changes one by one: accept what convinces you, change back what does not.
  • Share with a neighbor: one change you accepted, one you rejected, and why.
  • The refined plan is yours only after this pass.
Then

Execute the plan, stage by stage

Work through the plan on your own data, committing after each stage. Every commit message must be readable by a colleague.

Stage 1

Clean

Ask the agent to explore first:

What are the missing codes in my key variables? What types are they stored as?copy

Common problems it should find:

  • missing values coded as numbers (for example -1 to -5, or 999)
  • numbers stored as text
  • filters you meant to apply but never wrote down

Commit when the cleaned data prints sensible summaries.

Stage 2

Describe

  • Ask for the summaries that answer your question, not a dump of every variable.
  • For each table or figure, ask yourself: would I show this to a co-author as evidence?
  • Commit when the descriptives match what you know about your data.
Stage 3

Model

  • State the model in your own words first, then ask for a plan.
  • Review the plan for the choices that are yours: specification, standard errors, weights, sample.
  • Execute, read the output, and ask the agent to explain anything unexpected.
  • Commit with a message that names the model and the headline result.
If stuck

When you get stuck

  • When a command fails, let the agent read the error and fix it; if you are stuck yourself, describe what happened.
  • If the plan has a step you do not understand, ask the agent to explain that step; do not approve what you cannot explain.
  • Ask one of us for help. If your setup cannot be fixed, you work with a partner.
Try it

Check one result on your data

  • Take one number from this morning's analysis.
  • Check it a second way: recompute it, or compare it to a source you trust.
  • Ask the agent to explain that step, and find one choice you would have made differently.
  • If your two numbers do not agree, find out why before you go on.
Then

One formatted output

  • Produce one polished output from your model or descriptives: a table or a chart, styled the way your field expects.
  • The agent handles the formatting; you check the numbers.
  • Commit it to output/.

A second agent on your data

  • Ask the second agent to open your dataset and summarize its codebook while you keep working.
