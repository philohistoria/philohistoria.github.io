Breaking work into clear steps · do it on the right

Five stages of any analysis

  • Every empirical project moves through the same five stages:
    • Data preparation. Where does the data come from, and is it clean?
    • Exploratory analysis. What patterns are there?
    • Statistical modeling. Does the hypothesis hold?
    • Output and reporting. How do you present it?
    • Reproducible publication. Can someone else replicate it?
  • Today you work through stages 1 through 4 on your own data. Stage 5 is a build option on Friday.

First try: the vague prompt

The task is harder than Monday’s: build a multi-item index. Constructing a measure has real degrees of freedom, and that is where direction matters.

Using the WVS, measure how postmaterialist each country is and rank the countries.
  • A ranked chart comes back in two minutes, and it looks final.

Second try: the same task, directed

  • Explore: "Read the codebook. List every item in the materialist/postmaterialist battery, its wording, and its missing codes. Change nothing."
  • Plan: "Propose a plan for the standard four-item index and a country ranking. State your choice on missing codes, weights, and wave, and flag every place a published analysis might reasonably differ."

  • The vague run was not wrong anywhere you could point to. It was uncheckable, and that is the difference.

Coding data with the agent · do it on the right

Turning text into variables

  • A lot of social-science data starts as text: open-ended answers, interview transcripts, documents, news.
  • The agent can read each case and assign a code, the way a research assistant would.
  • That turns text into a variable you can count and model.

A worked example: 311 complaints

  • The running example: a city’s 311 complaint narratives, free-text descriptions residents typed in. The question: what are people actually complaining about?
  • The codebook is categories, each with a rule and an example:
    • Noise — the complaint is mainly about sound. "Upstairs neighbor plays drums past midnight."
    • Housing condition — about the building itself: heat, water, mold. "No heat in the apartment for three days."
    • Street and trash — about shared space outside. "Mattress on the corner for a week."
    • Other — anything else, plus a rule for mixed cases: code the main grievance, the one the resident wants fixed.
  • Give the agent the codebook and twenty cases, and read what it returns. Where it codes differently than you would, the rule was unclear; fix the rule, not the answer.

Who does the coding, mechanically

  • There are two setups, and the size of the data decides.
  • Dozens of cases: the agent reads them directly in the conversation and codes them, like an RA reading a stack of pages. This is how you develop the codebook and build your hand-coded comparison sample.
  • Thousands of cases: the agent writes a script that sends each narrative, with the codebook as the prompt, to a model API, one call per case, and writes the labels to a CSV. The script can rerun, resume after a crash, and call a cheaper model than the one you are talking to.
  • Do not have the agent read thousands of cases in the conversation itself: the session fills up, and the coding drifts as it fills.
  • Once the codebook is frozen, the prompt in that script is your measurement instrument. Freezing it is what makes the measure reportable.

Check the agent's codes against your own

  • Hand-code a random sample yourself, then compare the agent's codes to yours.
  • Report the agreement, the same way you would for two human coders.
  • Low agreement means the codebook is vague or the task is too hard; fix that before you trust the rest.

Then code the full dataset

  • Once agreement is high enough, let the agent code the full dataset.
  • Keep the sample and the agreement number; they are your evidence the measure is sound.
  • Spot-check a few more as it goes.

Verifying your results · do it on the right

Why you always check

  • The agent is fluent, and fluent output can still be wrong.
  • It will not tell you when it guessed; a wrong number looks exactly like a right one.
  • Nothing counts as a result until you have checked it yourself.

Ways to check a result

  • Recompute one number a second way, in software you already trust, and see if it matches.
  • Compare it against something you already know: a published figure, a total that must add up, or a number you expected.
  • Read the code and the choices it made: which cases it dropped, how it treated missing values, whether it weighted.
  • Look at the plain features of the data: the row count, the missing counts, the smallest and largest values.
  • Change one input, and check the output moves the way it should.
  • Have a fresh session or a second agent redo the step, and compare the two.

Worked example: Monday's chart

  • Monday's WVS chart looked convincing. It was probably wrong in at least one place:
    • Right variable? WVS has several politics items: interest, importance, action. Check the codebook.
    • Missing values? WVS codes "don't know / refused" as -1 to -5; averaging those in corrupts every country mean.
    • Weights? WVS has survey weights; unweighted means can mislead.
    • Scale direction? 1 = very important, 4 = not at all; the chart may run in the opposite direction from what you expect.
  • Every one of these is invisible in the picture and visible in the code.

Working faster: several agents at once · do it on the right

You can run more than one agent

  • You can open several agents at once.
  • Give each one a separate job, and they work at the same time.
  • One cleans the data, one draws a figure, one looks up the codebook, all at once.
  • The jobs have to be independent, so none of them waits on another.

Subagents: one agent runs the others

  • You do not have to open and manage the agents yourself.
  • You can tell one agent to do it: "clean the data, draw the figure, and look up the codebook, using a separate helper for each."
  • These helpers are called subagents. Each gets its own separate working context, does one assigned task, and returns a short report to the main agent.
  • The main conversation receives only the reports, so it does not fill up with the helpers’ working text.
  • You invoke them in plain language: asking for the work "in parallel, using separate subagents" is enough, and there is nothing to configure.

Which arrangement for which job

  • The two arrangements are alternatives. The difference is who coordinates the work, you or the main agent.
  • Open several sessions yourself when the tasks are independent and you want to watch and steer each one.
  • Use subagents when the results must be combined afterward. The main agent receives every report, so it can require one format for all of them.
  • When the combining step needs judgment, do it yourself: run separate sessions and merge the results.
  • On Thursday you use subagents on a real case: five papers read in parallel, then one synthesis.

Sessions can message each other

  • In both tools, one open session can send a message to another.
  • Claude Code: /msg list shows your reachable sessions, and /msg sends to one. This works without any setup, including to sessions on other machines.
  • Codex: a session can queue a message to another local or remote session.
  • Use it to coordinate your open sessions: the session that finishes cleaning tells the modeling session that the data is ready.
  • Shared files and git are the slower way to pass work between sessions. They also leave a record a collaborator can read later.

Use a large model to plan and small models to execute

  • Each vendor sells several model sizes. The large one is better at judgment and costs more per token. The small one is cheaper and faster.
  • A common arrangement uses both. The main agent runs on the large model and does the planning and the checking. The subagents run on the small model and do the mechanical work.
  • Planning is one short conversation and execution is many long ones, so you spend the expensive tokens on the judgment.
  • In practice: pick the model for a session with the tool’s model command, and tell the main agent to use a smaller model for its helpers.

What running them costs

  • The tool charges by usage, measured in units called tokens, and each plan has a limit.

Discussion and wrap

Discussion

  • Where did the agent surprise you, for better and for worse?
  • What did you catch when you read the code?
  • Would you have caught it without being told to look?

Why long sessions drift

  • As a session grows, the text the agent is holding from the session fills up with files, outputs, and errors.
  • Your instructions from the first hour get crowded out, and the agent slowly reverts to its own defaults.
  • Tomorrow morning it remembers nothing at all.
  • Tomorrow's session builds the fix: instructions that persist outside the conversation.

Hands-on

Exercise

Which mode would you pick?

For each task, decide which of the three modes fits:

  • First look at a collaborator's undocumented dataset.
  • Rerunning your validated cleaning script on this month's new wave.
  • Changing how your script treats missing income.
  • "Plan the analysis for my one-sentence question from last night."

There is a defensible answer for each; the point is that you choose the mode on purpose.

The task

Direct one analysis on your data

Start from the sentence you wrote last night, on your own data. Work through three stages, and commit after each:

  • Clean. Missing codes, variable types, sample filters.
  • Describe. The descriptives that matter for your question.
  • Model. One model suited to your question.

Two requirements:

  • Use plan mode (Claude Code) or a read-only sandbox (Codex) at least once, and change at least one thing in the plan before you run it.
  • Every commit message must be readable by a colleague.
Stage 1

Clean

Ask the agent to explore first:

What are the missing codes in my key variables? What types are they stored as?copy

Common problems it should find for you:

  • missing values coded as numbers (for example -1 to -5, or 999)
  • numbers stored as text
  • filters you meant to apply but never wrote down

Commit when the cleaned data prints sensible summaries.

Stage 2

Describe

  • Ask for the summaries that answer your question, and not for a generic dump of every variable.
  • For each table or figure, ask yourself: would I show this to a co-author as evidence?
  • Commit when the descriptives match what you know about your data.
Stage 3

Model

  • State the model in your own words first, then ask for a plan.
  • Review the plan for the choices that are yours: specification, standard errors, weights, sample.
  • Execute, read the output, and ask the agent to explain anything unexpected.
  • Commit with a message that names the model and the headline result.
If stuck

When you get stuck

  • When a command fails, let the agent read the error and fix it; if you are stuck yourself, describe what happened.
  • If the plan has a step you do not understand, ask the agent to explain that step; do not approve what you cannot explain.
  • Ask one of us for help. If your setup cannot be fixed, you work with a partner.
Try it

Code a slice of your own text

  • Take twenty text cases from your project and write a two-category codebook.
  • Have the agent code them, and hand-code the same twenty yourself.
  • Compare, and note where you and the agent disagree.
Try it

Check one result on your data

  • Take one number from this morning's analysis.
  • Check it a second way: recompute it, or compare it to a source you trust.
  • Ask the agent to explain that step, and find one choice you would have made differently.
  • If your two numbers do not agree, find out why before you go on.
Then

One formatted output

  • Produce one polished output from your model or descriptives: a table or a chart, styled the way your field expects.
  • The agent handles the formatting; you check the numbers.
  • Commit it to output/.
Try it

A second agent on your data

  • Keep your main agent open, and start a second one beside it.
  • Ask the second agent to open your dataset and summarize its codebook while you keep working.
  • You finished two things in the time of one.
