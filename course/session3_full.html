Why the agent is inconsistent

The same prompt gives different results

  • Run the same request on two different days and you can get:
    • a different table format
    • different standard errors
    • different treatment of missing data
  • Two structural reasons:
    • Every session starts blank, so the RA forgets between meetings.
    • A vague instruction leaves gaps, and the agent fills them with its own defaults.

What the agent decides for you when you do not

  • Unless you specify them, these are the agent's choices, made silently:
    • which standard errors to report
    • how to treat "don't know" and "refused"
    • whether to weight
    • how to round, sort, and label
    • what a table should look like
  • Any one of them can change what your reader concludes.

The fix: a specification that persists

  • Better prompting each morning does not fix this, because the same gaps reopen in the next session.
  • The fix is a written specification the agent reads at the start of every session, before you type anything.
  • The standard name is AGENTS.md, at the root of your project. Codex and most other agents read it directly.
  • Claude Code reads its own file instead, named CLAUDE.md; it does not read AGENTS.md. The two files do the same job, only the name differs.
  • So: Codex users write AGENTS.md, Claude Code users write CLAUDE.md. Everything below applies to both; where we say AGENTS.md, use your tool’s name.
  • It is the standard operating procedure for your AI assistant.

What goes into an AGENTS.md

  • Only what applies to every task in the project:
    • the research question and the data
    • methodological standards: weights, standard errors, missing rules
    • file and naming conventions
    • output formats
    • things the agent must never do
  • Keep it short. Write the page of rules you would give any new RA on day one, and nothing more.

Why this is worth the effort

  • Once your standards are written down, the agent applies them in every session, on your machine or a collaborator's.
  • The agent stops re-guessing your conventions, so it handles the same task the same way each time.
  • In one study across 138 projects, an instructions file cut the agent's mistakes by a third to a half.
An AGENTS.md that encodes your standards is the AI equivalent of a pre-registration.

Your AGENTS.md · do it on the right

The same prompt, two ways

  • Without AGENTS.md. The agent guesses: default standard errors, its own table format, silent choices about missing data.
  • With AGENTS.md. It applies your weighting rule and your table format without being asked.
  • The prompt is identical, and only the context differs.

What to watch in the side-by-side

  • The standard errors: the default against the ones the file requires.
  • The table: the agent's habit against your journal's format.
  • The missing data: silently dropped against handled by your written rule.
  • The model is no smarter. What changed is that your standards were in the file the agent reads.

The four sections

  • Write four sections for your own project:
    • Project context. The question, the data, the unit of analysis.
    • Data conventions. Key variables, units, missing-data policy.
    • Output standards. Table format, chart style, what every result must report.
    • Safety rules. What the agent must never do.
  • Write concrete lines: name your variables, your units, your journal.

Example lines: context and data conventions

  • Project context:
    • "Panel survey of 4,000 respondents, waves 2020 to 2024; unit of analysis is person-wave."
    • "The outcome is political participation; the key predictor is education."
  • Data conventions:
    • "All models use survey-weighted standard errors."
    • "Missing codes are -1 to -5; recode to NA before any computation."
    • "Never modify anything in data/raw/."

Example lines: output standards and safety rules

  • Output standards:
    • "Every table reports N and confidence intervals."
    • "Charts use one message per chart, with a full-sentence title."
    • "Summaries follow: Question, Method, Finding, Limitation."
  • Safety rules:
    • "Never fabricate a number; if a value is unavailable, say so."
    • "Always state the sample restriction used."
    • "Flag every result you could not verify."

Skills · do it on the right

What a Skill is

  • A Skill is one routine you repeat often, written down once and invoked whenever you need it.
  • Technically it is a Markdown file in your repo with a description the agent reads.
  • AGENTS.md holds the rules that apply always; a Skill holds one procedure you invoke when needed.
  • Two ways it fires:
    • the agent loads it automatically when the task matches its description
    • or you call it by name, like a command

Skills that work, and skills that do not

  • A Skill works when it is specific:
    • works: "My survey-weighted OLS table, with my SE choices, in my format."
    • fails: "A regression skill."
  • Good candidates from this class:
    • the descriptive panel you produce for every new dataset
    • your standard robustness battery
    • the data-prep sequence for each new wave of your survey
  • If a new RA could not follow the written routine, neither can the agent.

The format you just used is an open standard

  • The Skill you just wrote is a folder holding one plain-Markdown file, SKILL.md. Because it is plain text, you can audit a stranger's in minutes.
  • The format is an open standard (agentskills.io), adopted by roughly 20 agents including Cursor, Codex, and GitHub Copilot, so a Skill written once runs in all of them.
  • One public directory, skills.sh, counts over 1.1 million skill installs.
  • The practical consequence: for many research routines, someone has already written the Skill, and you can read exactly what you would be adopting.

Four ways to install one

  • Clone (either tool). Clone the repository, then copy or symlink the skill folders you want. open-scholar-skill ships a bash setup.sh that does the copying for you.
  • Official catalog (either tool). Each vendor ships one. Claude Code registers Anthropic’s marketplace the first time you start it, so you install by name with /plugin install. In Codex you type $skill-installer inside the session and name a skill from the openai/skills catalog.
  • Third-party marketplace (Claude Code). Add someone’s repository as a marketplace, then install by name. Claude Code shows the token cost and the full list of what will install before anything lands on disk.
  • Cross-agent (either tool). The skills CLI installs from any public git repository into whichever agents you have. The skills.sh directory is a search index over public repositories, and anyone can appear in it — it is not a curated store.
  • Whichever route you take, the result is a folder you can open. A skill in your home skills folder applies to everything you own; a skill inside a repository travels with that project.

Where an installed skill sits on disk

  • Installing a skill means putting a folder with a SKILL.md in a place your agent reads, and nothing else.
  • Both tools read a home location and a project location. Home applies to every project you open; the project location travels with the repository when you share it.
  • Claude Code reads ~/.claude/skills/ and .claude/skills/; Codex reads ~/.agents/skills/, ~/.codex/skills/, and .agents/skills/.
  • The two tools do not read each other’s folders. Codex ships an /import command that copies Claude Code skills and settings across.

Updating a skill you installed

  • An installed skill is a snapshot. The author keeps editing theirs; yours does not change until you update it.
  • Cloned: git pull in the clone, then re-run setup.sh or copy again. A copied folder does not receive the pull; a symlinked one does.
  • Claude Code marketplace: Anthropic’s own marketplaces update in the background and then ask you to run /reload-plugins. Third-party marketplaces do not update on their own: run /plugin marketplace update, or switch auto-update on in the /plugin menu.
  • Cross-agent: npx skills update re-fetches every skill from its source; name one to update just that one.
  • Codex catalog: there is no update command; run $skill-installer on the skill again.
  • An update rewrites instructions your agent will follow, so read the changes the way you read the skill before installing it. An update also overwrites edits you made in that folder; keep your own edits under a different skill name.

Installing without the terminal

  • The Claude Code desktop app installs plugins from a window: the + next to the prompt box → Plugins → Add plugin opens a browser of your marketplaces, and Manage plugins turns them on and off.
  • Codex has no install window. The IDE extension lists your skills, and the installer runs as a command typed inside the session.
  • Neither tool has a window that installs a plain skill folder; that is still a matter of putting the folder in the right place, which is what the commands on this page do for you.
  • The desktop apps read the same folders the terminal reads, so a skill installed either way shows up in both.

Installing a Skill is a trust decision

  • A Skill is instructions your agent will follow, so installing one means trusting whoever wrote it.
  • Sources fall into three tiers: official collections from the tool vendors; people you know, such as a coauthor or labmate sharing a private repository; and strangers on the internet. The first two you can install after a quick read; the third you read line by line first.
  • Snyk's ToxicSkills study (2026) found prompt injection in 36% of the agent skills it examined, and 1,467 malicious payloads on a single skill registry (ClawHub).
  • A skill body can embed dynamic-context syntax that runs shell commands the moment the skill loads, before any human reads it.
  • Anthropic's own documentation says: "Only install plugins and add marketplaces from sources you trust."
  • The rule in this course: read the SKILL.md before you install, and check the allowed-tools grant and any embedded shell command.

What is shared and what stays yours

  • Everything that defines your agent’s behavior in a project is a file in the project folder: the context file, .claude/agents/, and the skill folders. Whoever gets the folder gets your setup.
  • Your home folder ~/.claude/ is different: it holds your personal skills, your settings, and the agent’s memory of you. It applies to every project on your machine, and it is not part of any shared folder.
  • So the rule has two halves: the project folder is the shared unit, and the home folder is yours.
  • Never share: settings.local.json, API keys, and anything under ~/.claude/.
  • The simplest sharing is one-way: copy someone’s project folder and keep what you want. You get a snapshot, and their later changes reach you only when you copy again.

Collaborating through a shared Dropbox folder

  • For two or three people who trust each other, a shared Dropbox or Drive folder is the easiest route: the files sync on their own, and nobody learns a new tool.
  • One working rule makes it safe: do not edit the same file at the same time. Split the files between you, or say who is editing what.
  • If you break the rule, Dropbox keeps both versions and renames one AGENTS (conflicted copy 2026-04-15).md. Nothing is lost, but you merge the two by hand.
  • Dropbox keeps versions per file for a limited time (30 days on Basic, 180 on Business), with no record of why a change was made.
  • One warning: do not put a git repository inside a synced folder. Two machines writing its internal files at the same moment can corrupt it. Data in Dropbox, code in git, is the standard split.

Collaborating through git: both of you commit

  • On Monday you learned one git move: commit a save point. Collaboration adds one more: pull, which fetches your partner’s commits.
  • Nobody has to approve anyone. One of you creates the repository and adds the other as a collaborator; from then on both push changes directly. Review steps exist on GitHub, and they are optional and off by default.
  • The creator alone controls the settings: who is invited, public or private, deletion. Over the code itself, you are equals.
  • The routine that prevents almost all trouble: pull before you start, then edit, then commit and push.
  • When you both changed the same file anyway, the later push is rejected. That is protection, not failure: pull first, and git merges the file on its own when you touched different lines. Only when you edited the same lines does it stop, put both versions side by side in the file, and wait for you to choose.
  • Nothing is ever silently overwritten. This record of who changed what, and the automatic merging, are what git adds over the shared folder.

The agent runs git for both of you

  • Neither of you memorizes git commands. Start a session with “pull the latest,” end it with “commit and push, the change was about X.”
  • When a push is rejected or a merge stops, say “resolve it and show me what you kept.”
  • Add one line to your context file: confirm with me before pushing. Without it the agent will stage, commit, and push in one step, and the change leaves your machine before you have read it.

Editing a Skill you adopted

  • You can edit any Skill you adopt: copy the folder into your home skills folder, edit SKILL.md, and the change applies immediately, with no restart.
  • Renaming the directory renames the command; rewriting the description field changes when it fires on its own.
  • The cleanest worked example: Yanbo Zhang's my-scientific-taste is a deliberately replaceable placeholder holding your scientific taste, which his other skills consult by name.
  • His rule for where things belong matches the split you built today:
What is true for everyonegoes in a shared Skill
What is true for yougoes in my-scientific-taste
What is true for this projectgoes in AGENTS.md

Managing your usage · do it on the right

The agent bills by the token

  • Everything you send and everything it writes is counted in tokens, against the plan limit you first met on Tuesday.
  • A long session, a big file pasted in, or many rounds of back-and-forth all run the count up.
  • Running several agents at once spends it several times as fast.

How to spend less

  • Use a smaller, cheaper model for simple steps, and save the strong one for the hard ones.
  • Give a tight brief so it gets there in fewer rounds.
  • Start a fresh session for a new task, so it is not re-reading an old one.
  • Point it at just the one file it needs.
