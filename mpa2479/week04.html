APIs and public data · do it on the right

API requests and parameters

  • An API lets programs request data or services from another system. An endpoint is the address used for a particular request.
  • Parameters specify what data you want. For example:
    • which agency,
    • which dates,
    • which fields.
  • A data API returns a response that your script can read and save, often in a structured format such as JSON.
  • Saving the request in a script lets you repeat the collection or change its parameters. Save the response too, because the source may change.
  • Some APIs require an API key to identify or authorize requests. Keep keys out of Git. The Federal Register API used here requires no key.

Collecting Federal Register documents

  • Collect up to 100 rules and proposed rules published in 2025 by one agency from the Federal Register API. Record how those records were selected.
  • Create a separate analysis table and summarize the collected documents by month. Label the summary as the collected subset.
  • Change the agency and rerun.
  • Then open several of the collected records on federalregister.gov and compare the saved title, date, and abstract with the published page.

Raw data and source documentation

  • Keep an unchanged copy of the raw response in data/.
  • Record the collection details:
    • the full request URL,
    • the parameters you sent,
    • the date and time of collection.
  • Cleaning happens in the script, so the cleaned table can always be rebuilt from the raw file.
  • These details document the data’s provenance: where it came from and how it was collected.

Rerunning the collection · do it on the right

Checking the README with a classmate

  • Exchange GitHub repositories with a neighbor and rerun the collection from their README alone.
  • Try the README first and record any clarification you need.
  • A failed rerun can reveal a missing dependency, file, or instruction.
  • Tell your classmate which files, dependencies, or instructions were missing.
  • Revise the README using this feedback.
  • Keep the abstracts for Week 5. For Checkpoint 2, adapt the collection to your own project’s data source.

Web scraping · optional extension

Collecting an HTML table

  • Some sources publish tables on web pages without offering an API or a downloadable data file.
  • The agent can read the page and write a script that extracts the table into a data file.
  • Save a copy of the page and record its URL and collection date.
  • A layout change can cause the extraction script to fail or collect the wrong content. Check the extracted rows against the page.
  • Check for a downloadable file or API before writing a scraper. For repeated collection, test whether the extraction still works each time.

HTTP error codes

HTTP status code reference

CodeWhat happenedWhat to do
403the server refused the requestcheck access requirements, credentials, and the response message
404the requested resource was not foundcheck the documentation for the current address
429the requests came too fastfollow the retry guidance and reduce the request rate
500the server itself failedwait and try again
  • The status code helps diagnose a failed request. Read the response message and check the source documentation.
  • If you cannot access the source, look for a published download or an alternative source.

Parallel source checks · do it on the right

Script loops and subagents

  • For repeated requests to the same API, use a script loop to change the agency, place, or date.
  • For different sources that require separate investigation, use the subagents introduced in Week 3.
  • Give each agent a source to inspect and the same questions: what data are available, what period they cover, and how to collect them.
  • Compare the reports and check their source links before choosing a collection method.

Project and policy discussion

Evidence and the policy question

  • What does the source record, and who or what is absent?
  • Does the available evidence fit your question? How might it change the problem or the alternatives worth considering?
  • Where did AI help you find or collect evidence, and where did you need additional work?

Hands-on

Step 1

Read the API documentation

Open the Federal Register API documentation and choose an agency for the classroom exercise.

  • The Federal Register API needs no key. Write the script in scripts/.
Step 2

Collect up to 100 documents

Send the agent the parameters for your chosen agency:

Write a script that uses the Federal Register API to collect up to 100 rules and proposed rules published in 2025 by [agency]. Keep the document number, publication date, agency, title, abstract, and source link. Record the sort order and selection rule. Report how many records were returned and flag missing abstracts. Save the raw response in data/ without editing it, and write a note next to it with the full request URL, the parameters, and the date and time of collection.copy
  • Read the request URL it built. You should be able to say what every parameter in it does.
Step 3

Check the collected records

Clean the raw file into an analysis table in a separate step, and produce one formatted output in output/: a table or chart of the collected documents by month, labeled as a subset. Do not modify the raw file.copy
  • Open several collected records on federalregister.gov and compare the saved title, date, and abstract with the published page.
  • If the request fails, inspect the error message and the request parameters with the agent.
Step 4

Change one parameter

  • Rerun with a different agency or a different date range.
  • Check whether the saved parameters and instructions are enough to reproduce the new collection.
  • Review the changed files and commit the collection script and documentation.
  • Write the README with the source, parameters, dependencies, and commands needed to rerun the collection. Push the files needed for the rerun to your GitHub repository.
Step 1

Exchange GitHub repositories

  • Exchange GitHub repository links with a neighbor.
  • Follow their README and record any step that needs clarification.
Step 2

Report problems with the rerun

  • Did it run? If not, at which step did it stop?
  • What did you have to guess, and what would have told you the answer?
  • Hand your neighbor that list.
  • Revise your README and begin adapting the workflow to your project’s data source for Checkpoint 2.
If your own pipeline is not running yet, do this in reverse: watch your neighbor try to run what you have, and write down where they stop.
