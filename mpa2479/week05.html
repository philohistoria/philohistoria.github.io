What text coding is

Turning text into a variable

  • Much policy information comes as text. Administrative records such as rules, public comments, court filings, and inspection notes are mostly text.
  • Surveys contain text too, whenever people answer a question in their own words.
  • Text coding turns that text into a variable. You read each document and assign it one value from a fixed set of categories.
  • A codebook is the written rule for that assignment. It names the variable, lists the categories, and defines each category with an example.

Text coding in research and government

  • Researchers code text to build the variables their analysis needs.
    • The Manifesto Project codes the election platforms of more than 1,400 parties since 1945. Coders assign each sentence to one of 56 policy categories, such as “Free Market Economy”. The codebook is public.
    • The Comparative Agendas Project codes government activity in about 20 countries and regions into the same 21 policy topics. Researchers use it to compare what governments pay attention to.
  • Governments code text to produce official statistics.
    • The American Community Survey asks people to describe their job in their own words. The Census Bureau codes each answer into one of about 570 occupation categories. Different answers for the same job, such as “nurse”, “RN”, and “registered nurse”, must get the same code.
    • The Bureau of Labor Statistics codes written descriptions of workplace injuries. Each case gets codes for the occupation, the injury, the part of the body, and what caused it.

Writing a codebook

A draft codebook for federal rules

  • Today everyone codes the Federal Register abstracts collected in Week 4. Each of you chose a different agency, so the question must work for any agency.
  • The question for each abstract: does this rule add regulation, reduce it, or neither?
  • The Federal Register labels each document by type and agency. These labels do not answer the question. You need to read the abstract.
  • I wrote a first codebook with three categories.
    • Stricter: the rule adds or tightens a requirement, limit, fee, or standard.
    • Looser: the rule removes, delays, exempts, or eases a requirement.
    • Technical: the rule corrects, clarifies, or extends a deadline without changing what anyone must do.
  • This codebook is a first draft. In the exercise below, you test it on your own abstracts and improve it.

Exercise 1: Revising the draft codebook

  • Code 10 abstracts from your agency with this codebook.
  • If you were writing this codebook, how would you make it clearer? Rewrite it.

Exercise 2: A codebook for your own project

  • Pick text from your own project, such as state laws, incident reports, or public comments. Write a short codebook for one variable.
  • Swap with a classmate who does not know your topic. Your partner codes 5 of your documents using only the codebook. Do not explain anything while they code.
  • Compare their codes with yours. Where you disagree, find the part of the codebook that misled them.
  • A large language model reads your codebook the same way your partner did. It knows only what the codebook says.

The scale problem

The volume of policy text

  • A federal agency can publish hundreds of rules in a year. In 2025 the EPA published 242 proposed rules.
  • In 2012 the Census Bureau reported that it assigns more than 2 million industry and occupation codes to survey answers every year (Thompson, Kornbau & Vesely 2012).
  • A public comment period can draw far more documents. The FCC received more than 22 million comments on net neutrality in 2017 (New York Attorney General 2021).
  • At that scale, hand coding takes too long. Researchers and agencies use computers to code the text.

How computers code text

Three common approaches

  • The dictionary method uses keyword rules. You list keywords for each category. A document gets a category when it contains that category’s keywords.
    • RegData measures the amount of federal regulation by counting the words “shall”, “must”, “may not”, “required”, and “prohibited”.
  • Supervised machine learning trains a model on a large number of hand-coded documents.
    • The Bureau of Labor Statistics trained its injury coder on past cases that its staff had coded by hand. The model now assigns most of the codes.
    • The Census Bureau codes occupations the same way. Answers the model is unsure about go to staff coders.
    • This course does not teach supervised machine learning.
  • Large language models code text from a prompt. The prompt contains the codebook, the text, and a request for a category. There are two common ways to write the prompt.
    • Zero-shot: the prompt contains only the codebook and the text. It needs no coded examples.
    • Few-shot: the prompt also contains a handful of coded examples.
    • Agencies are now testing large language models for this work. In April 2026, Census Bureau researchers presented their work on coding occupations with large language models.
  • Today you code with a large language model and zero-shot prompts. A dictionary method serves as a simple comparison.
  • The reading by Gilardi and colleagues compares coding by ChatGPT with coding by crowd workers.

Coding the pilot with the agent · do it on the right

Coding the pilot abstracts

  • Ask the agent to code the 10 abstracts you coded by hand. The agent reads your codebook and each abstract, and returns one category per abstract.
  • Compare its codes with yours. Where they differ, read the abstract again.
    • The definition may be unclear.
    • The agent may have made a mistake.
    • You may have made a mistake.
  • Revise the codebook and ask again.
  • If the agent codes these 10 abstracts poorly, a script will code hundreds of abstracts poorly. Fix the codebook first.

Zero-shot and few-shot

  • So far the agent has seen only your codebook. This is zero-shot coding.
  • For few-shot coding, add 2 or 3 coded abstracts to the codebook as examples. Choose abstracts from categories the agent got wrong.
  • Take the examples only from these 10 abstracts.
  • Keep both versions of the codebook. Later you test both on new abstracts.

Scaling up with a script · do it on the right

Model APIs

  • In Week 4 your script sent a request to the Federal Register API. The request named an agency and a year. The API sent back documents.
  • A model API works the same way. Your script sends a request, and the API sends back the model’s answer.
  • Here the request contains your codebook and one abstract. The answer is the model’s category for that abstract.

Commercial and open-source models

  • Commercial models run on the company’s servers. You pay for each call, and your text goes to the company. Each company documents its API:
    • OpenAI API (GPT models)
    • Anthropic API (Claude models)
    • Google Gemini API
  • A chat subscription such as ChatGPT Plus does not include API access. The API is billed separately.
  • Open-source models can be downloaded and run by anyone.
    • Hugging Face hosts most open-source models, such as Llama, Qwen, and Gemma.
    • Ollama runs these models on your own computer and gives them a local API. Your data stays on your computer.
    • They are free to run, but usually less capable than the best commercial models.
  • Find the API documentation for the model you want to use. Give the link to the agent when it writes the script.

The coding script

  • The agent coded 10 abstracts inside the conversation. For hundreds of abstracts, every abstract should get exactly the same instructions.
  • Ask the agent to write a script. The script sends your codebook and one abstract at a time to a model through its API. It saves the category for each abstract in a table.
  • Each call to a commercial API costs money. You pay for the text you send and the text you get back. Ask the agent to estimate the cost before you run the script.
  • Record the exact model name and version. Companies update their models, and the same prompt can give different codes after an update.

Validating with a held-out sample · do it on the right

Held-out evaluation

  • Think of a student who memorizes last year’s exam answers. The student scores 100% on that exam and fails a new one.
  • Your codebook is in the same position. You revised it until the agent coded the 10 pilot abstracts well. A score on those 10 abstracts says little about new abstracts.
  • A fair test uses new abstracts that played no part in writing the codebook. These abstracts are the held-out sample.
  • Freeze the codebook. After this point you do not change it.
  • Pick 20 new abstracts. Code them by hand before you see any model codes.
  • Run the script on these 20 abstracts twice: once with the zero-shot codebook and once with the few-shot codebook.
  • Real projects hand-code more documents for this test. Twenty abstracts are enough to practice.

More detail: other ways to compare codes

When the agreement rate misleads

  • Suppose 16 of your 20 abstracts are Technical.
  • A model that answers Technical every time agrees with you on 16 of 20 abstracts, or 80%.
  • That model never finds a Stricter or a Looser rule. A high agreement rate can hide a model that misses the rare categories.

Precision and recall

  • Precision and recall describe one category at a time. Take Stricter in the example table above.
  • Precision: of the abstracts the model coded Stricter, how many did you code Stricter? The model coded 8 abstracts Stricter, and 6 of them match yours. Precision is 6 of 8, or 75%.
  • Recall: of the abstracts you coded Stricter, how many did the model find? You coded 7 abstracts Stricter, and the model found 6. Recall is 6 of 7, or 86%.
  • Which one matters depends on the policy question.
    • To find every rule that tightened regulation, you need high recall.
    • To report how many rules tightened regulation, you also need high precision.
  • The F1 score combines precision and recall into one number. It is low when either one is low.

Agreement between two people

  • When two people code the same documents, their agreement is called intercoder reliability.
  • Cohen’s kappa is the common measure. It counts agreement beyond what two coders would reach by chance.
  • A common rule of thumb: kappa of 0.6 or more is acceptable, and 0.8 or more is strong.
  • Exercise 2 tests the same thing. If two people cannot agree on a code, there is no answer against which to judge the model.

Consistency checks

  • A good measure gives the same codes when nothing important changes. Check this in three ways.
    • Same model, same codebook: run the held-out sample twice. The two runs should give the same codes.
    • Different wording: your zero-shot and few-shot versions are two wordings of the same task. Small changes in wording can change the codes. This is called prompt sensitivity.
    • Different model: run the held-out sample with a model from another company, or with an open-source model.
  • Compare the confusion matrices. If the codes change a lot, read the abstracts whose codes changed. The codebook may be unclear for those abstracts.

Dictionary baseline

  • The dictionary method gives a simple benchmark. If the language model cannot beat a list of keywords, it is not worth its cost.
  • Read the 10 pilot abstracts and list keywords for each category.
    • Looser: “withdraw”, “delay”, “rescind”.
    • Stricter: “require”, “establish”.
    • Technical: “correction”, “technical amendment”.
  • Ask the agent to code the 20 held-out abstracts with your keyword lists.
  • Build the same confusion matrix and compare it with the language model’s.

Choosing the model

Accuracy, cost, and data rules

  • Compare the held-out results: zero-shot against few-shot, and each model you tried.
  • Look closely at the categories that matter most for your question.
  • Estimate the cost of coding your full collection.
  • Check whether your data may be sent to a company’s servers. Restricted data needs a local model or an approved arrangement.
  • Write down the chosen model, its version, the final codebook, and the held-out results.

Project and policy discussion

Text coding in your project

  • Does your project need text coding like today’s, or could it use it?
  • If so, which text would you code, and which variable would you build from it?
  • Many projects rely mostly on numbers. Coding plays a small part in those projects.
