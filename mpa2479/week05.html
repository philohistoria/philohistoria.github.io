AI for data coding and model choice

Authors: Han Zhang and Codex (OpenAI)

Construct a measure, evaluate it on held-out human codes, and explain whether it is useful for the intended policy analysis.

From text to a measure

Today, define a variable, ask a model to code text, and check its labels against your own. Use the abstracts collected in Week 4 or suitable text from your individual project.

Readings

Evaluating AI text annotation

  • Gilardi, Alizadeh & Kubli, “ChatGPT outperforms crowd workers for text-annotation tasks” (2023). Focus on how annotation performance is evaluated.

Text coding and codebooks · do it on the right

What text coding means

  • Policy analysis often uses text such as rule abstracts, public comments, permit applications, and inspection notes.
  • Coding is assigning each document a value on a variable you defined.
  • A codebook is the written rule for that assignment: the variable, its categories, and what each category means.
  • The coding prompt gives the model the codebook, the text to label, and the required output format. Save the codebook and prompt.
  • Use a fixed version of the codebook for each coding run so that every document is judged by the same rules.
  • Record the codebook version used for each set of labels.

Choosing a variable and categories

  • The shared exercise uses the Federal Register abstracts you collected in Week 4.
  • The variable is the policy action the document describes.
  • Read 10 abstracts and draft your categories, with a name and definition for each. Discuss difficult cases with a classmate.
  • The Federal Register document type and agency labels describe different categories. Use them as context when reading the abstracts.
  • Use your own project text if coding it would help answer your question.

Piloting the codebook

Comparing human and model codes

  • Label the 10 pilot abstracts yourself before seeing the model labels. Then ask the model to code the same texts.
  • Inspect disagreements. They may reflect unclear categories, model mistakes, or mistakes in your own codes.
  • Revise the definitions and examples, then test again. Save each version.

Held-out evaluation

  • Save a fixed codebook after the pilot. Use it to label 20 different abstracts before seeing the model labels.
  • This is the held-out sample: texts you did not use to develop the codebook. Compare human and model labels on these texts.
  • Use the pilot texts for debugging. Keep the human evaluation labels out of the model’s input.

Coding with a script · do it on the right

Batch coding with a model API

  • Ask the agent to write a script using your fixed codebook.
  • The script sends each abstract to a model API with the frozen codebook and writes the codes to a CSV.
  • Use the script to send the same frozen coding instructions with each abstract. Keep the inputs and output identifiers consistent.
  • Test a lower-cost model and use validation to judge its performance.
  • The CSV needs the document number, the code, and the name of the model that produced it.
  • Save the script, codebook, model details, and resulting labels so you can trace how each code was produced.

Writing the coding script

Write a script in scripts/ that accepts an input file of abstracts, sends each abstract to the model API with the codebook in codebook_frozen.md, and writes one row per abstract to a specified output CSV with the document number, the code, and the model name. Keep human labels out of the API requests. Retry a failed request once; if it still fails, record a missing code and the error.
  • Ask the agent to explain one API request. Check that it contains the abstract, the unchanged codebook, and the output instructions. It should not contain your human labels.
  • Test the script on 5 pilot abstracts before running the held-out sample. Check the output format and document IDs.
  • Run the script yourself or ask the agent to run it.

Validating the measure

Confusion matrices

  • Compare the model codes with the 20 held-out human codes. Rows show human categories and columns show model categories.
  • Cells outside the diagonal show disagreements. Read those abstracts and explain which errors would matter for your policy question.
  • Compare the model with a keyword baseline: simple category rules based on words in the text. Develop those rules on the pilot and evaluate them on the same held-out sample.

Larger batches and model comparisons

  • Code a larger batch of abstracts with the frozen codebook, or try a second model on the same 20. Record the model and version.
  • Use disagreements to identify cases to inspect. Models can share errors even when they come from different families.
  • If the evaluation leads you to change the codebook or select a model, describe that change and use fresh data for a new evaluation.

Choosing the model

Performance, cost, and data requirements

  • Compare validation results for the categories that matter to the project.
  • Estimate the cost of the planned batch and check the model’s output format and failure handling.
  • Check the source terms and any applicable data agreement before sending documents to a model service.
  • Use the public Federal Register abstracts for this exercise. Projects with restricted data need an approved processing arrangement; a suitable local model may be an option.
  • Record the selected model, version, codebook, and evaluation.

Project and policy discussion

Measures and evaluation criteria

  • What does the coded variable measure, and how would it help answer your question or compare alternatives?
  • Which errors matter for that use? Does your validation support using these codes?
  • What did AI make easier, and what did defining and checking the measure still require?

Step 1

Write the coding script

Write a script in scripts/ that accepts an input file of abstracts, sends each one to the model API with the frozen codebook, and writes a specified output CSV with the document number, the code, and the model name. Keep human labels out of the API requests. Retry a failed request once; if it still fails, record a missing code and the error.copy

Step 2

Check the script before evaluation

  • Run the script yourself or ask the agent to run it.
  • Test on 5 pilot abstracts. Check the returned labels, document IDs, and any error messages.
  • Then run the 20 held-out abstracts with the fixed codebook and save output/codes.csv. Report successful and failed requests separately.
  • Commit the script, the frozen codebook, and the CSV together.
Step 1

Build the confusion matrix

Join output/codes.csv to data/handcodes.csv on document number. Check for duplicate or missing IDs. Build a confusion matrix with human labels as rows and model labels as columns. Report failed or missing model codes separately, overall agreement among completed cases, and the proportion matched within each human category.copy
  • Find the off-diagonal cells and read those abstracts yourself.
  • Explain two disagreements in writing, and say what the model confuses with what.
Step 2

Build a keyword baseline

Use only the pilot texts and pilot labels to define keyword rules for my categories. Save the rules before applying them to the evaluation texts. Compare those predictions with data/handcodes.csv and build a confusion matrix.copy
  • Compare the two matrices. Does the model beat the baseline, and in which categories?
Step 3 · extension

A larger batch or a second model

  • Code a larger batch of abstracts with the frozen codebook, or code the same 20 again with a model from a different family.
  • For a second model, compare its held-out performance and inspect disagreements. For a larger batch, record completion and failure counts.
