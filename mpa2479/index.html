MPA 2479, Applied AI for Public Policy: Weekly Schedule

This is a course which is part of the Master of Public Affairs program and the program is at the Watson Institute, Brown University and it takes place in Fall 2026.

Thursdays from 9:00 to 11:30 am and the instructor is Han Zhang.

Teaching goals

1. Learn to use agentic AI and find out what it cannot do. Students install the agent in Week 1, run it themselves after that, check every output against a source or their own hand-coding, and find the limits by running into them.

2. Next, use the agent for policy analysis, which follows the standard framework from Bardach & Patashnik's A Practical Guide for Policy Analysis. The course goes through its eight steps in order, and students choose a policy question in Week 3.

3. Treat AI policy as its own domain. Regulating AI is a separate question from using an agent for policy work. Students analyze it with the same eight steps and look at government AI systems in Week 8 and choices among governance approaches in Week 10 and use the agent to collect evidence for that analysis too.

Week 2Sept 17Shopping Directing the agent
  • Git: a commit takes a snapshot of your files. The agent runs git commands, and you read what it did.
  • Analysts keep a history for three reasons. They can return to a working version, see how the analysis evolved, and show a teammate what changed.
  • Keep raw data out of the tracked history before the first commit, and pushing a repository publishes it, so never put 311 or police records in it.
  • Write a clear message for every commit and after the first commit, ask the agent to show the history.
  • Work in a pair and Pull before you start. Then edit, commit and push. A rejected push protects your partner's work and the agent runs every command.
  • The repository stores the spec, .claude/, and your own machine keeps ~/.claude/ and API keys.
  • Can your data leave your machine? If it cannot, you can run a model on your own machine using Ollama and turn off the wifi to prove nothing is being sent. Make this decision before you choose your dataset in Week 3.
  • There are three ways to run the agent: Normal mode: You approve each step, Auto-accept mode: The agent accepts steps automatically, and Plan mode: The agent writes a plan and you approve or edit the plan before anything runs.
  • Demo: Do the same task with a vague prompt and then do it with a directed one.

Week 5Oct 8Eightfold pathStep 2b: evidence Coding text at scale: making your measures
  • Use the agent to change text into variables, and the text includes consumer complaints, public comments, and permits.
  • The prompt is the tool. Freeze it and then run it.
  • First, pilot the process and code a small overlap sample twice and use two independent coders. Compare both against your own hand codes and revise the codebook until agreement stops improving and each revision is a new version of the prompt.
  • First, freeze the codebook. The agent writes a script which sends each document to a model API using the frozen codebook and writes the codes to a CSV file. A cheap model is enough and the agent does not read the documents and subagents are not the coders.
  • API prices are low and coding everything again with a different model family costs little. Using the same model family twice repeats the same errors, which is like one coder coding twice, so you must resolve the disagreements.
  • The tier question is this: Can you check every result yourself, and if you cannot, you need a gold standard.
  • Confusion matrix and a simple baseline to compare against.
 Build and validate your measure
  • The course uses the CFPB Consumer Complaint Database, which has 3.8 million public consumer complaint narratives. There is no registration, and you can use an API at consumerfinance.gov or a bulk CSV, or use your own data instead if your project has text.
  • Coding tasks are the main grievance type. There are four categories: UNAUTHORIZED means money moved or an account opened without consent, INACCURATE_RECORD means the company reports something wrong; the remedy is a correction instead of money, UNFAIR_CHARGE means the account is yours but you dispute the charge or rate, and SERVICE_FAILURE means the company would not act or could not be reached. These four categories cross CFPB's own product and issue labels, so those labels serve as a third rater.
  • Hand-code 100 narratives yourself
  • Test the codebook on a small sample with some overlap, do two independent coding runs, and add your own hand codes. Revise the codebook, run it again, and stop when agreement no longer improves.
  • Freeze the codebook and tell the agent to write a script which will use the API and code 1,000 narratives. Use a cheap model and write the codes to a CSV.
  • Compare these things: The confusion matrix, your 100, and a two-feature baseline.
  • Please paste the text you'd like me to rewrite, and I will follow the instructions exactly.

  • Internal AI-Use Policy — Government Analyst Office Purpose and scope: This one-page policy governs use of AI tools by office analysts for drafting, research, data processing, and decision support, and it applies to all staff, contractors, and temporary personnel. Decision summary: After weighing trade-offs between usability, security, cost, and agility, the office adopts a hybrid approach: on-premise or government-approved models for sensitive work, vetted commercial tools for low-risk tasks, mandatory human review for all analytic outputs, and centralized logging and oversight. 1. Data classification and handling Policy: Always classify data before using it with any AI tool, and handle each classification level according to the approved handling rules. Trade-offs and decision: Automating classification speeds work but risks mislabeling; manual classification is slower but safer, so use automated tagging with mandatory human spot-checks for High/Secret data. My experience this term: My experience this term showed automated tags caught routine labels and human review corrected edge cases, so we adopt mixed automation plus human verification. 2. Approved models and infrastructure Policy: Use only models and platforms on the approved list for the corresponding data classification; High/Secret processing must occur on on-prem or physically isolated government systems. Trade-offs and decision: On-prem systems increase cost and maintenance burden but minimize exfiltration risk, and external APIs improve speed and features but raise leakage concerns, so require on-prem for sensitive work and vetted commercial services for unclassified tasks. My experience this term: My experience this term found external APIs accelerated drafting of public summaries but introduced uncertainties for controlled material, so we require on-prem for sensitive contexts. 3. Human-in-the-loop and final approval Policy: Analysts must review and approve all AI-generated content before dissemination, and disclaim AI assistance in documents when appropriate. Trade-offs and decision: Full manual work ensures accountability but reduces throughput, while full automation increases speed but lowers trust, so mandate human review for all outputs and allow limited automation for drafts and routine checks. My experience this term: My experience this term showed that AI drafts saved time but contained errors requiring human corrections, so human approval remains mandatory. 4. Provenance, logging, and retention Policy: Log all AI interactions with metadata (user, tool, model version, input dataset classification, purpose) and retain logs per records schedules. Trade-offs and decision: Detailed logs aid audits but consume storage and raise privacy concerns, so log essential metadata centrally with access controls and retention aligned to classification. My experience this term: My experience this term revealed gaps in traceability when logs were sparse, so we require standardized minimal metadata for each interaction. 5. Data sharing and external uploads Policy: Do not upload Controlled, Confidential, or Classified data to external or commercial AI services unless explicit authorization is granted for a specific exception and compensating controls exist. Trade-offs and decision: Allowing uploads to commercial services speeds collaboration but risks exposure, and prohibiting uploads reduces flexibility, so prohibit uploads by default and permit exceptions with formal approvals. My experience this term: My experience this term included incidents where inadvertent uploads caused review delays, so we prohibit uploads absent authorization. 6. Model validation and benchmarking Policy: Validate models for accuracy, bias, and robustness against representative test sets before operational use and revalidate after major updates. Trade-offs and decision: Extensive validation requires time and expertise but reduces downstream errors, while limited checks are faster but risk deployment failures, so implement a staged validation regimen proportional to risk. My experience this term: My experience this term showed small validation suites missed systematic errors, so we require representative tests before use. 7. Documentation and provenance of outputs Policy: Analysts must record the model, version, prompts, and post-processing steps used to produce analytic outputs and must include caveats about known limitations. Trade-offs and decision: Detailed documentation increases workload but improves reproducibility and accountability, so require concise standardized provenance records with templates to reduce burden. My experience this term: My experience this term demonstrated that clear provenance accelerated error tracing, so we standardize brief provenance entries. 8. Training, awareness, and role-based access Policy: Provide mandatory training on AI capabilities, risks, and safe practices, and assign role-based access controls to tools and data. Trade-offs and decision: Broad access promotes innovation but increases risk of misuse, while tight controls protect information but can slow work, so combine targeted access with regular training and a lightweight approval process for new tools. My experience this term: My experience this term found trained users made fewer policy violations, so we require recurring training and controlled access. 9. Incident reporting and remediation Policy: Immediately report suspected data leaks, model misuse, or anomalous outputs to the AI oversight officer and follow remediation steps. Trade-offs and decision: Rapid reporting limits damage but can generate false alarms, so use a triage process that prioritizes confirmed exposures while tracking all reports. My experience this term: My experience this term showed early reports prevented escalation in one case and generated false positives in another, so we implement triage and follow-up. 10. Exceptions and governance Policy: Exceptions require written justification, risk assessment, and approval by the AI oversight officer and the data owner. Trade-offs and decision: Strict rules reduce flexibility, and a formal exceptions process provides controlled flexibility, so implement a documented, time-limited exception pathway. My experience this term: My experience this term indicated that a formal exception process resolved urgent needs without undermining controls, so we formalize that route. Enforcement and review: Compliance is mandatory and subject to audits; the policy will be reviewed quarterly to incorporate operational lessons and technology changes, and updates will be communicated to all staff. Contact: Direct questions, exception requests, or incident reports to the AI oversight officer.
